# WhatsApp Embedded Signup v4 and Coexistence

Implemented 9 October 2026 in the existing RGCRM checkout. Automated implementation checks pass; **release remains blocked on deployment, Meta dashboard verification, and actual live onboarding in both modes**. No remote migrations, deployment, customer messages, provider transfers, or AiSensy connection changes were performed.

Review fixes: verified Coexistence now atomically updates attempt modes and staged metadata, with a database registration gate and protected replay of phone-number-first callbacks. Phone-less lifecycle events resolve only an unambiguous connection or an exact supplied display number. Capture uses one RPC per webhook; processing uses one bounded RPC for up to 25 receipt batches. Tokens and phone IDs are validated before sync intent reservation; accepted and uncertain requests are never blindly resent. Migrations 77–78 were edited in place because the operator confirmed they have not been applied. No additional tables, dependencies, endpoints or corrective migrations were added during this review.

Final corrections preserve the authenticated start's Business App choice on generic `FINISH` events and reject contradictory registration activation. Unresolved lifecycle identity logs only a structured warning/count. Only the three supported Coexistence lifecycle events are intercepted; other account updates remain on the existing webhook path. History terminal states cannot regress; contact data is marked `received`, not complete, with explicit UI wording and terminal-state preservation. The official Business App guide was rechecked; no contact-completion signal was inferred. Meta research MCP remains unavailable.

Final simplification removed the registration and activation alias/wrapper pairs by updating their existing guarded functions directly. The lease wrapper remains necessary for the mode-aware signature and unchanged lease engine. Settings uses the requested two connection choices and Advanced Options for manual setup, with readable sync statuses. Signup errors expose numeric Meta codes, safe trace IDs and credential-redacted user-facing text; raw provider errors remain private.

## Persistence, recovery and deployment

Apply forward migrations **77 then 78**, after existing 73–76, before deploying the matching backend/frontend. Quiesce signup while changing the RPC wrappers. Do not alter historical migrations. Test against a staging copy with the complete existing schema before production rollout.

The only new table is a private webhook receipt ledger, `whatsapp_coexistence_events`. It is required to retain acknowledged large chunks across `after()` termination; it is not another connection, message store, webhook endpoint or automation queue. Existing `whatsapp_config`, contacts, conversations and messages remain canonical. Migration 78 adds import provenance/contact app-state columns and a SQL job to the **existing pg_cron infrastructure**. Confirm pg_cron is available and the `whatsapp-coexistence-import` job is scheduled and executing. Each wake-up imports at most 25 batches of 100 records; backlogs drain over subsequent runs.

Receipts resolve the workspace from the canonical WABA and phone, reject phone-less message imports, and use per-connection event hashes plus Meta message IDs. Transactions atomically import and mark a batch complete; failures roll back, retain a bounded SQLSTATE and retry with backoff, stopping after ten attempts. Settings exposes pending/exhausted counts. Processed payloads are cleared. Admin-only **Refresh and recover synchronization** retries local retained batches and starts only sync types with no existing API intent inside the deadline. It never resends an accepted or uncertain one-time Meta request. Unknown outcomes require Meta reconciliation, not a blind retry. The private ledger has no user-facing payload access.

History imports neither trigger inbound automation nor increase unread counts. New live messages retain existing behavior; a live message already seen in history can be promoted once. Out-of-order history never replaces newer conversation summaries. Contact removal records an app-state tombstone and preserves the CRM contact/history. Media placeholders are explicit; available media enriches the same message through the existing authenticated media endpoint. Missing/expired historical media is not fabricated. Meta history 100% is shown separately from pending local import counts; contact receipt state means updates are arriving, not proof of a complete address book.

Offboarding timestamps are ordered, and events predating a fresh onboarding cannot disconnect its new generation. Automatic reconnection keeps existing sync state. A confirmed fresh signup after partner removal establishes a new generation; queued old-generation payloads are discarded. All recovery retains the existing user/account/lease and encrypted-token guards.

**Environment:** no new variables, secrets or dependency changes. Existing `META_APP_SECRET`, optional single-app `META_EMBEDDED_SIGNUP_APP_SECRET`, Supabase credentials, encryption settings and correct HTTPS `NEXT_PUBLIC_SITE_URL` remain required. The deleted configuration ID has no remaining repository references, including accessible local configuration; no environment or checked-in deployment file needed replacement. Remote deployment variables/configurations were not accessible or changed: inspect them for stale overrides and rebuild/redeploy the frontend with the new ID. Never paste tokens or secrets into logs or reports.
